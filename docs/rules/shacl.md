### Module external

Source: `src/ontolint/rules/external.py`.

Specifications for rules that are not run by a graph rule module.

SHACL001 and SEM001 are produced by adapters (pySHACL, ROBOT) and INPUT001/TOOL001 by the CLI front end.  They carry ``module=""`` because no ``run(ctx)`` function emits them.

SHACL001 and SEM001 are findings: they appear in the report, gate the exit code through ``--fail-on`` (``1``), and obey ``--select``/``--ignore``, baselines and ``severity_overrides``.  INPUT001 and TOOL001 are diagnostics printed on stderr as ``<ID>: <message>`` with exit code ``2``; the selection never affects them, so naming them in ``--select`` or ``--ignore`` (by id, or as the ``INPUT`` or ``TOOL`` family) is a configuration error (``TOOL001``, exit ``2``), and naming them in the policy's ``ignored_rules`` or ``severity_overrides`` is ``GOV020``.

## Rules

#### SHACL001: SHACL validation violation

- **Severity:** error
- **Scope:** shapes
- **Category:** deterministic
- **Module:** [`external`](#module-external)
- **Fix:** Fix the supplied SHACL shapes or data, and inspect the SHACL report.

**Specification.** Only with ``--shapes FILE`` (the shapes file passes the safe loader) and pySHACL installed (``unsupported`` otherwise, which exits ``2``).  The data graph (merged, with ``--follow-imports``, with the ontology the shapes import, keeping only results whose focus, or the focus of a result nested in their ``detail``, the linted file mentions, as a subject or an object) is validated with ``inference="none"``, ``advanced=True``, ``meta_shacl=True``, with the network disabled (a socket or DNS attempt, even one pySHACL catches, makes the rule ``failed``).  One finding per value of the report's ``sh:result`` (SHACL 3.6.1.2) of the report node that is the object of no triple (a blank data value shaped like a report, which pySHACL copies into its report, adds no finding), or per typed ``sh:ValidationResult`` when the report links none, focused on its ``sh:focusNode`` (a blank node by its content-stable id), with the result messages joined by ``; `` and ``[shape: <source shape>]``.  The severity is that result's, so for an ``sh:node`` violation its referencing shape's: ``sh:Violation`` error, ``sh:Warning`` warning, ``sh:Info`` info, any other value error with ``(severity <value>)`` appended; the spec's ``error`` is only the default shown in rule listings.  Each finding's ``evidence`` (JSON ``evidence``, SARIF ``properties.evidence``) holds every SHACL result property listed below, under its SHACL name, in this order and only when present: ``focusNode``, ``resultPath``, ``value``, ``sourceShape``, ``sourceConstraintComponent``, ``sourceConstraint``, ``detail``, ``resultMessage`` (sorted, without language tags), ``resultSeverity`` (the original IRI).  SHACL-AF result annotations (``sh:resultAnnotation`` on a SPARQL-based constraint or constraint component; SHACL Advanced Features, section 4 "Annotation Properties") are not implemented by pySHACL 0.40.2, so they appear neither in its report nor in the evidence; a canary test fails when a pySHACL upgrade starts writing them.  IRIs are plain, blank nodes the content-stable ``_:`` id (data terms in the data graph, shapes terms in the shapes graph), literals one-line N-Triples, a complex path SPARQL 1.1 property-path syntax, or ``(malformed path)`` when it does not parse or exceeds 32 levels or 1,000 nodes; ``detail`` nests the ``sh:detail`` results, sorted, at most 8 deep, never around a cycle; nested results are their parent's ``detail``, not findings (SHACL 3.5), and one nested deeper than 8 appears in no output.  Findings tied on focus and message are ordered by their evidence, since pySHACL's result order depends on the hash seed.  The evidence is not part of the finding's identity: messages and fingerprints are unchanged.  Text prints it after ``Fix:`` and any ``In:`` line: ``Path: <resultPath>``, ``Value: <value>`` (left out when there is no path and the value is the focus) and one ``Detail: <focus>: <messages> [shape: <shape>]`` line per nested result, its own lines two spaces further in; control, format, surrogate, private-use and non-space separator characters are written as ``\uXXXX`` or ``\UXXXXXXXX``.  A non-conforming report without result nodes gives one error on ``(shapes)``, without evidence.  A shapes graph refused by the pre-check (unserialisable IRI, cyclic, shared or overlong ``rdf:list``) or a pySHACL crash makes the rule ``failed`` (no finding, TOOL001 line, exit ``2``).  With ``max_validation_seconds`` (``--max-validation-seconds``; default unset, in process) the validation of each file runs in a worker process, with the same findings and failure details, and is stopped at the budget: ``failed`` with ``ValidationTimeout: SHACL validation did not finish within the time budget of <s> seconds (max_validation_seconds)``, the report written, exit ``2``.  Confidence ``certain``: the verdict is pySHACL's, on the user's own shapes. Why error: a violated shape is a contract the user wrote; a shape that means less says so with ``sh:severity``. A shapes graph that breaks SHACL-SHACL (pySHACL's ``meta_shacl=True`` refuses it before any data is validated) gives no verdict on the data: the rule is ``failed`` and the exit code ``2``, as for any crash, but the run does not print pySHACL's report (which it prints in the exception and logs at ERROR).  The rule-execution line reads ``the shapes graph does not conform to SHACL-SHACL``; the ``TOOL001`` line is followed by one two-space indented line per MetaSHACL result, sorted, ``<focus>: <path>: <message>`` (no path for a node-level result), masked and cut at 300 characters, with control, format and separator characters escaped, at most 20 and then ``... and N more result(s) not shown``, each printed once.  A line ends with ``(SHQ023)``, ``(SHQ008)``, ``(SHQ014)`` or ``(SHQ022)`` when that rule fires on the same shape for the same defect (a property shape with no or several ``sh:path``, a count or length that is no ``xsd:integer``, a non-IRI ``sh:severity``, a non-IRI ``sh:targetClass``, ``sh:targetSubjectsOf`` or ``sh:targetObjectsOf``), and has no pointer otherwise.  JSON and SARIF carry the lines as ``results`` of the execution (``executions[].results``, the notification's ``properties.results``), only when there are some.  The shapes graph is meta-validated a second time, to read the results, only when pySHACL reported the failure, inside the worker and the ``max_validation_seconds`` budget when there is one.  A failure that is not a verdict on the shapes graph (a crash, pySHACL's own load errors, such as a typed ``sh:NodeShape`` with ``sh:path``) keeps its ``<ExceptionType>: <message>`` detail.
